# Spam hardening and safe duplicate merging
The existing PR55 durable PostgreSQL/Redis guard remains mandatory: business/contact hourly caps, honeypot, reservation expiry and token-owned release/complete. No memory fallback or direct anonymous DB writes. A server-only SQL RPC additionally serializes matching business + normalized email + normalized phone pairs; repeat enquiries within 7 days increment a counter and add activity without overwriting name, notes, score or status. The +91/10-digit Indian phone forms normalize consistently. Different tenants or differing contact pairs never merge. Repeat merges do not generate fresh confirmation/alert jobs. Rapid guard-denied repeats remain denied, rather than bypassing throttling to merge.

Manual setup: review/apply migration 04 only to the restored isolated copy first; verify concurrency and existing guard tests. Configure LEADFLOW_DUPLICATE_MERGE_ENABLED=true only after production backup and explicit migration approval. Keep PUBLIC_ENQUIRIES_ENABLED=false until the PR55 release gates pass. No new secrets or redirects. Existing LEAD_GUARD_PROVIDER=postgres and LEAD_GUARD_HASH_SECRET remain required.

Risks: shared contact details can belong to several people, so merging conservatively requires both email and phone and preserves original details. Manual owner-created leads are not rewritten or retroactively deduplicated. Spam can exhaust tenant quota; CAPTCHA is a future option if observed abuse warrants it. Estimated incremental monthly infrastructure cost ₹0 using the existing database; no new service or plan.

Rollback: turn merge flag off to return to guarded inserts. Keep counters/activity to preserve evidence. Schema rollback 04 is destructive metadata removal, for disposable staging only after export. Never bypass the guard as a rollback.
